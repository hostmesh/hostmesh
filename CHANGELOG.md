- CI workflow that starts the development stack and runs its smoke test on pull requests that touch `infrastructure/development/`.
- `php` service in the development stack: PHP-FPM 8.5.11 with the PostgreSQL, Redis, `intl`, `pcntl` and code-coverage extensions and Composer 2.10.3. It runs as the host user and mounts `control-plane/`.

- Identities in the control plane: `Administrator` (table `administrators`) and `User` (table `users`, portal logins) in `app/Domain/Identity`, with UUIDv7 keys, bcrypt-hashed passwords and emails stored in lower case. Each has its own session guard (`admin`, `customer`) and auth provider, so an account of one side can never authenticate on the other.
- Laravel Sanctum 4.3 for cookie-based SPA authentication.
- Session realms (`realm:admin`, `realm:customer`, `App\Http\Middleware\UseSessionRealm`): each route group accepts only its own SPA origin and has its own guard, session cookie (`__Host-hostmesh-admin-session`, `__Host-hostmesh-portal-session`), session table and idle lifetime (30 and 120 minutes, `HOSTMESH_ADMIN_SESSION_LIFETIME` and `HOSTMESH_PORTAL_SESSION_LIFETIME`). Session cookies are host-only, `Secure`, `HttpOnly` and `SameSite=Lax`.
- `GET /api/v1/admin/auth/csrf-cookie` and `GET /api/v1/customer/auth/csrf-cookie`: start the CSRF cookie flow. Each app has its own CSRF cookie (`XSRF-TOKEN-ADMIN`, `XSRF-TOKEN-PORTAL`) and echoes it in `X-XSRF-TOKEN`.
- Authentication endpoints for both apps: `POST …/auth/login`, `POST …/auth/logout` and `GET …/auth/user` under `/api/v1/admin` (administrators) and `/api/v1/customer` (portal users). A wrong password and an unknown email produce identical responses; login regenerates the session ID and logout ends the session on the server.
- Login rate limit: 5 attempts per minute for one email from one address and 20 per minute per address, counted per realm, answered with 429 and `Retry-After` whether or not the account exists.
- A portal session cannot reach admin endpoints and an admin session cannot reach portal endpoints: a request from the other app's origin is refused with 403, and a session ID of one realm means nothing in the other.
- Decision record 0010: session realms on top of Sanctum.

- Decision record 0011: TOTP two-factor authentication on `pragmarx/google2fa` instead of Laravel Fortify.
- Two-factor state on administrators and users: the TOTP secret (encrypted at rest), the confirmation time, the last accepted time step and the recovery codes (stored as SHA-256 hashes).
- TOTP engine in the control plane (`App\Domain\Identity\TwoFactor\Totp`, implemented on `pragmarx/google2fa`): 6 digits, 30-second steps, one step of clock drift either way, and a code is refused once it was accepted.
- Two-factor enrollment in both API groups: `POST auth/two-factor` returns a TOTP secret and its `otpauth://` URI, and `POST auth/two-factor/confirm` turns two-factor on with a valid code and returns ten recovery codes once.
- Two-factor login challenge in both API groups: `POST auth/two-factor/challenge` completes a login with a TOTP code or a single-use recovery code, refuses a code that was already used, and is limited to 5 attempts per minute for one account.
- Second-factor gate (`two-factor` middleware): every admin route except CSRF cookie, login, logout and the challenge answers 403 with `code: two_factor_required` or `two_factor_enrollment_required` until the session has completed two-factor authentication, which is mandatory for administrators and optional for customers. A test reads the route list, so admin routes added later are covered.
- `DELETE auth/two-factor` and `POST auth/two-factor/recovery-codes` in both API groups: disabling two-factor and replacing the recovery codes each need the current password and a valid code.
- Two-factor authentication in the OpenAPI document and the typed client, and in the authentication section of `control-plane/README.md`.
- Audit log in the control plane (decision 0013): the interface `App\Domain\Audit\AuditLog`, the value object `AuditEvent`, and the table `audit_events`, which PostgreSQL triggers keep append-only. Only `ip_address` and `user_agent` can be cleared, and only events older than 12 months can be deleted.
- Application events that implement `App\Application\Events\Audited` are written to the audit log by one synchronous listener, inside the transaction of the command that dispatched them.
- Every response from an API route carries `X-Request-Id`, generated by the control plane. A request that matches no route (404, 405) has none. The audit log stores it with the request's IP address and user agent.
- Audit events for login success, login failure and logout in both realms. A failed login for an unknown address stores a keyed hash of the address, never the address. A login or logout whose audit event cannot be written does not happen.
- Audit events for two-factor authentication in both realms: enrollment started, confirmed, disabled, recovery codes regenerated, challenge passed, challenge failed (with the method tried) and recovery code used (with the number left). No secret, code or recovery code is stored, and a change whose audit event cannot be written is rolled back.
- Application commands `AssignAdministratorRole` and `RevokeAdministratorRole`, which change `administrator_roles` and write the audit event (`administrator.role_assigned`, `administrator.role_revoked`) in one transaction. They have no HTTP endpoint yet.
- `GET /api/v1/admin/audit-events`: the audit log, newest first, cursor paginated and filtered by actor, resource, action and time. It needs the new permission `audit-event.view`, which the roles `owner` and `read-only` hold. Display names are resolved when the log is read and are null for an account that is gone.

- "Audit log" section in `control-plane/README.md`, with the rules for a new audited action.
- Decision record 0014: job history in the table `job_history`, attempts counted in PostgreSQL, no Laravel Horizon.
- Table `job_history` and the application service `JobHistory`: one row per operation with its type, resource, generation, node, status, failure class, last message, attempts and start and finish times (decision 0014).
- `RetryPolicy` for one-shot jobs: exponential backoff from 10 seconds with jitter, capped at 10 minutes, 8 attempts, and a 2-minute recheck for waiting jobs. Every number is configurable through `HOSTMESH_JOB_RETRY_BASE_DELAY`, `HOSTMESH_JOB_RETRY_MAX_DELAY`, `HOSTMESH_JOB_RETRY_MAX_ATTEMPTS`, `HOSTMESH_JOB_RETRY_JITTER` and `HOSTMESH_JOB_RECHECK_DELAY`.
- Base class `OneShotJob` for one-shot actions on the Redis queue, with the failure handling of spec section 8: a retryable failure backs off and fails after the attempt limit, a waiting job is rechecked without using up an attempt, a terminal failure fails at once, and a run that was interrupted counts as one attempt. A job delivered a second time while its first run is inside the timeout waits and counts nothing. A job says which class it hit by throwing `JobFailure`; any other exception is reported and treated as retryable, and the row stores its class name only. Failed jobs are also stored in `failed_jobs`.
- One-shot job `retry_reconcile` (`App\Application\Jobs\RetryReconcile`) and the application command `DispatchOneShotJob`, which writes the history row and pushes the job after the transaction commits. The job does nothing yet except leave its row: no managed resource exists before Slice 1, and no endpoint calls it.
- Tests that keep Redis out of correctness: sessions, failed jobs and job batches stay in PostgreSQL, Redis is declared for the queue and the cache only, and the application uses no direct Redis call, lock, unique job, overlap guard or cache-backed attempt counter.
- `worker` service in the development stack: it runs `php artisan queue:listen redis`, so queued jobs run during development. Run `make -C infrastructure/development up` once to start it. The smoke test checks that its `queue:listen` process is running.

- Brand colors in the control plane's domain layer: `#rrggbb` parsing and the WCAG contrast check of a `primary` and `primary_foreground` pair against the default light and dark surfaces (4.5:1).

It carries `Cache-Control: public, max-age=300` and an `ETag`, and answers `304` to a matching `If-None-Match`. Stored in the new table `branding`.

Colors must be `#rrggbb`, links `https` URLs of at most 2048 characters, the product name at most 60 characters without control characters. A color that fails WCAG AA is saved and reported in `warnings`. Every change writes the audit event `branding.updated` with the names of the changed fields; a save that changes nothing writes none.

The type is read from the bytes (`finfo` and `getimagesize()`), the file is stored on the new `branding` filesystem disk under a name derived from its content, and the client's file name and content type are never used. Changes write the audit events `branding.image_replaced` and `branding.image_removed`.

Exceptions are per package, name the one license they cover and carry a reason; an exception that matches nothing fails the scan. `infrastructure/hygiene/README.md` has the procedure and lists the services that run as separate processes and are not linked (PowerDNS, MariaDB and others).
- `THIRD_PARTY_NOTICES`, generated by `make -C infrastructure/hygiene notices`: the license and notice files of the third-party source code in the repository (the shadcn-vue components of `@hostmesh/ui`, the Laravel application skeleton) and of the production dependencies of the control plane, both web apps and the agent. It prints no version numbers, so it changes only when a production dependency is added, removed or relicensed. `make -C infrastructure/hygiene notices-check` fails when the committed file is out of date.
- SPDX identifier check: `make -C infrastructure/hygiene spdx` fails when a tracked source file lacks `SPDX-License-Identifier` in its first 10 lines. Vendor, generated, lock and third-party-derived files are exempt by an explicit pattern with a reason in `infrastructure/hygiene/spdx.toml`; an exempt file that claims Apache-2.0, or an exemption that matches nothing, fails the check.
- SPDX identifiers on the four issue templates, and `Apache-2.0 AND MIT` on the three control-plane files that grew out of the Laravel skeleton (`AppServiceProvider.php`, `bootstrap/app.php`, `bootstrap/providers.php`).
- CI workflow `Hygiene`, on every pull request and on `main`, without a path filter so that its jobs can be required: `Hygiene tool checks` (ruff, mypy, pytest of `infrastructure/hygiene/`), `License scan` (the allowlist, and `THIRD_PARTY_NOTICES` being up to date) and `SPDX identifiers`.
- `.github/dependabot.yml`: weekly version updates for Composer (`control-plane/`), npm (`web/`), uv (`agent/`, `infrastructure/testing/`, `infrastructure/hygiene/`) and GitHub Actions. Minor and patch releases are grouped into one pull request per ecosystem, and titles start with `chore`.
- CONTRIBUTING: an alias and a `prepare-commit-msg` hook that sign off every commit, how to repair a missing sign-off, and the checkpoint of decision 0002 before the first outside contribution.
- The DCO check and the license scan were each proven to fail: a throwaway pull request with an unsigned commit that added a GPL-licensed dependency failed `Signed-off-by check` and `License scan`. The repository settings that make the checks required are listed in the pull request that introduced them.
- `TRADEMARKS.md`, the trademark policy: what may be done with the Hostmesh name without asking (truthful references, compatibility and "based on" statements, running it under an operator's own brand, distributing it unchanged), what needs permission (naming a product or a changed version "Hostmesh", implying endorsement, using the name in domains, package names and accounts), and how to ask. The README links to it.
- OpenAPI generation fails instead of writing an incomplete document. `composer openapi` now exits with an error that lists every problem when Scramble cannot read the rules of a `FormRequest` or cannot infer a type; before, it exported the request without its body or the field as a string. The settings are in `AppServiceProvider`, so the contract test and CI share them. `control-plane/README.md` says what to do for each kind of problem.
- A contract test that fails when a route under `/api/v1` has no name or when an operation's ID is not its route name, and the convention for operation IDs in `control-plane/README.md`.
